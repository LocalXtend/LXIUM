# 마법소녀의 마녀재판 분석

게임 파일을 REA(Ghidra 디컴파일)와 에셋 분석으로 뜯어 보고, 왜 무거운지 정리한 문서입니다. 게임은 실행하지 않고 파일만 읽었습니다.

> 정확한 근거(함수 주소, REA 근거 ID, 수치)는 AI용 문서 [`../ai/mahosaba.md`](../ai/mahosaba.md)에 있습니다. 두 문서는 항상 같이 고칩니다.

## 한 줄 결론

**캐릭터 한 명을 "매 프레임 사진 찍어 붙이는" 구조**이고, 그 사진기가 **3D 게임용 무거운 설정**을 그대로 달고 있습니다. 재판 장면에서는 3D 법정을 그리는 카메라 두 대가 더해집니다.

## 게임은 어떻게 생겼나

- Unity 6 (6000.0.48f1), IL2CPP 빌드, 노벨 엔진은 **Naninovel 1.20**
- 렌더 파이프라인은 URP인데, 2D용이 아니라 **3D 기본 템플릿 설정(URP-HighFidelity)** 을 그대로 씁니다
  - 안티에일리어싱 MSAA 4배, 화면 공간 그림자 효과(SSAO), 중간 텍스처 항상 사용
  - 2D 노벨 화면에서는 거의 효과가 없는데 비용은 그대로 냅니다
- 모드 생태계는 BepInEx 하나라서, LXIUM도 BepInEx 6(IL2CPP)용으로 만듭니다
- 한글 패치는 번들 28개(중국어 간체 텍스트 자리, UI·연출 번들)를 바꾸는 방식입니다. LXIUM은 번들을 건드리지 않아 같이 쓸 수 있습니다

## 그림은 어떻게 그려지나

| 대상 | 방식 |
|---|---|
| 주연 13명 (에마, 히로, 메루루 …) | **레이어 캐릭터**. 팔·표정·땀 같은 조각 그림(43~126장)을 겹쳐 한 장으로 합성 |
| 크리처·간수 등 18명 | 다이스 스프라이트 (잘게 쪼갠 그림을 다시 맞춤) |
| 배경 | 4096×2048 그림 한 장 |
| 재판 법정 | 진짜 3D 장면 (빛 계산하는 재질, 조명 2개, 불 효과) |
| UI·대사 | 메인 카메라가 같이 그림 |

## 캐릭터 하나가 왜 벅찬가

캐릭터가 화면에 있는 동안, **표정이 그대로여도** 프레임마다 이런 일이 일어납니다.

1. 캐릭터 안에 숨은 전용 카메라가 조각 그림을 모아 **1500×3000 사진**을 찍습니다 (화면 1080p의 2.2배 크기)
   - 이 카메라도 3D 설정을 그대로 받아 SSAO와 중간 텍스처 복사까지 합니다
   - Naninovel 설명서도 이 "카메라 방식"을 "덜 최적화된 방식"이라고 적어 둡니다
   - 캐릭터 설정의 `animated`가 켜져 있어 "매 프레임 다시 찍으라"는 뜻입니다
2. 찍은 사진을 전환 효과용 셰이더로 **한 번 더 복사**합니다 (매 프레임, 바뀌었는지 확인하지 않음)
3. 그 사진을 화면에 붙입니다

캐릭터에는 애니메이터도, 입 모양 자동 움직임도 없습니다. 표정은 대본 명령으로 바뀔 때만 바뀝니다. 즉 **같은 사진을 1초에 60번 다시 찍는 것**이 가장 큰 낭비입니다. 원본 그림도 캐릭터당 8192×8192(64 MB) 한 장이라, 처음 등장할 때 메모리를 크게 씁니다.

배경도 같은 "복사" 단계를 거쳐서, 4096×2048 그림을 매 프레임 한 번씩 다시 복사합니다.

> 1번이 정말 매 프레임인지는 정적 분석만으로는 호출 위치를 못 찾아서, 렌더 실험실로 직접 세어 확인할 예정입니다.

## 게임 자체 렌더링도 문제인가 — 네

- 재판 장면은 3D 법정을 **카메라 두 대**가 각각 1920×1080으로 그리고, 그걸 화면 분할로 보여 줍니다
- 게임은 무대를 띄우면 **두 카메라를 항상 같이** 켭니다. 한 화면만 보일 때도 두 대가 다 그리는 것으로 보입니다
- 두 카메라 모두 빛 계산 재질 + 불 셰이더 + SSAO + MSAA 2배 + FXAA를 합니다
- 그래서 재판 중에는 "메인 카메라 + 법정 카메라 2대 + 캐릭터 수"만큼 무거운 렌더가 매 프레임 돕니다
- 말씀하신 대로 **입자(파티클)는 초당 1개 수준이라 원인이 아닙니다**. 다만 불 효과는 큰 판에 무거운 셰이더를 칠하는 방식이라 픽셀 비용이 있습니다
  - 불 셰이더를 디스어셈블해 보니 픽셀마다 텍스처를 8번 읽습니다 (깊이, 노이즈 3장, 마스크, 그라데이션, 그리고 비어 있어서 늘 같은 값인 텍스처 2장)
  - 불 판은 25개(크기 20~25 유닛)이고, 연출 때만 켜집니다. 지금까지 잰 대화 장면에서는 꺼져 있었습니다 (화면의 불꽃 무늬는 스테인드글라스 그림)

## GUI·글자는 쓸데없이 다시 그리나 — 아니요, 대신 짐을 같이 짊어짐

- 대사·메뉴가 매 프레임 쓸데없이 다시 만들어지는 증거는 없습니다
- 다만 UI는 별도 카메라 없이 메인 카메라에 그려져서, 메인 카메라의 MSAA 4배·SSAO·FXAA 비용을 같이 냅니다. FXAA는 글자를 살짝 흐리게도 합니다
- 메뉴 글자에 그림자 효과(TrueShadow)가 390개 붙어 있습니다. 그림자 그림은 바뀔 때만 다시 만들지만, 숨겨진 화면에서도 매 프레임 확인 작업은 도는 것으로 보입니다 (작은 CPU 비용, 측정 예정)
- 글꼴은 처음 나오는 글자를 그때그때 만드는 방식이라, 새 글자가 많이 나올 때 아주 짧은 끊김이 있을 수 있습니다

## 프레임 제한

- 게임 옵션은 60/30fps 두 가지뿐이고, VSync는 그래픽 품질 단계가 정합니다
- 게임 코드에서는 VSync를 바꾸는 함수가 빌드 과정에서 빠져 있어서, LXIUM은 엔진 내부 호출로 직접 바꿉니다

## 실제로 해 보니 (1차, LXIUM 0.1.0)

- 재판 장면이 원래 10fps도 안 나왔는데, 기본 설정 그대로 **60fps가 계속 유지**됩니다 (Iris Xe 노트북)
- 60은 모니터 주사율(60Hz)에 맞춘 상한이라, 실제로는 더 여유가 있을 수 있습니다. `TargetFps = -1`로 풀면 알 수 있습니다
- 어떤 기능이 얼마나 기여했는지는 아직 모릅니다. 렌더 실험실이 꺼져 있어서(`RenderLab = false`) F10이 동작하지 않았습니다
- 실행 로그로 분석 내용(3D 템플릿 설정, 법정 카메라 2대·1920×1080)이 실제와 같음을 확인했습니다
- 게임이 1366×768로 실행 중이라 캐릭터는 원래의 53% 배율(800×1600)로 합성됐습니다. 해상도를 바꾸면 그 뒤에 새로 만들어지는 캐릭터부터 맞춰지고, 이미 화면에 있는 캐릭터는 그대로입니다

## 렌더 실험실로 재 보니 (2차, 재판 장면, 1366×768 창 모드)

| 단계 | fps | 프레임당 ms |
|---|---|---|
| 원래 상태 | 22.5 | 44.4 |
| + 2D 카메라 MSAA 끄기 | 22.8 | 43.9 |
| + SSAO는 법정에만 | 30.2 | 33.1 |
| + 중간 텍스처 필요할 때만 | 30.4 | 32.9 |
| + 바뀔 때만 다시 그리기 | 41.7 | 24.0 |
| + 안 보이는 법정 카메라 끄기 | **72.3** | **13.8** |

- 3.2배 빨라졌습니다. (캐릭터 해상도 맞춤은 실험 중에 끌 수 없어서 "원래 상태"에도 켜져 있었습니다. 진짜 원래는 더 느립니다)
- 크게 효과 본 세 가지: SSAO 정리(-10.8ms), 바뀔 때만 다시 그리기(-8.9ms), 안 보이는 법정 카메라 끄기(-10.2ms)
- **추측이 맞았습니다**
  - 화면에는 캐릭터가 2명뿐인데 **11명이 매 프레임 합성**되고 있었습니다. 카메라에 안 잡히는 다른 단상의 참가자까지 계속 사진을 찍고 있었던 것
  - 한 화면만 보일 때도 **두 번째 법정 카메라가 계속 그리고 있었습니다**
- 단계별 스크린샷을 화소 단위로 비교해도 차이가 없습니다 (불 흔들림·압축 잡음 수준). 화질 손해 없이 빨라진 것입니다
- 1초마다 한 번씩 하는 안전 갱신이 11명분 한 프레임에 몰려 약간의 끊김(최대 23ms)이 있었습니다 → 0.1.1에서 프레임마다 하나씩 나눠 하도록 고침
- 법정 카메라가 창(1366×768)보다 큰 1920×1080으로 그리고 있었습니다 → 0.1.1에서 화면 크기에 맞춤

## 0.1.1로 다시 재 보니 (3차, 같은 재판 장면)

| 단계 | fps | 프레임당 ms |
|---|---|---|
| 원래 상태 | 23.4 | 42.7 |
| … (2차와 같은 단계들) | … | … |
| + 안 보이는 법정 카메라 끄기 | 72.3 | 13.8 |
| + 법정 해상도를 화면에 맞춤 | **115.1** | **8.7** |

- **원래보다 4.9배** 빨라졌습니다 (23 → 115fps). 2차와 같은 단계의 수치도 거의 같게 나와서 측정이 믿을 만합니다
- 1초마다 생기던 짧은 끊김이 줄었습니다 (가장 느린 1% 프레임 22.9 → 17.7ms)
- 법정 해상도 맞춤은 확대해서 비교하면 벽지 무늬 같은 아주 세밀한 부분이 살짝 덜 또렷합니다. 원래는 큰 그림을 줄여 보여 줘서 생기던 덤 선명함이 빠진 것이고, 보통 화면에서는 구분하기 어렵습니다. 신경 쓰이면 `Stage Resolution = 1`

## 0.2.0 실행 확인

- 타이틀 화면까지 켜 보고, LXIUM 불 셰이더(FireLite)가 게임 안에서 정상적으로 불러와지고 Direct3D 11에서 지원된다는 것을 확인했습니다. 오류는 없습니다
- 새 실험들의 효과는 렌더 실험실(4차)로 잴 예정입니다

## 아직 모르는 것

- 1080p 전체 화면에서의 수치
- 메뉴 그림자 확인 작업의 실제 CPU 비용
- 불이 켜진 장면에서 불 셰이더가 실제로 얼마나 무거운지

## 게임이 업데이트되면

AI용 문서 2장의 식별값(GameAssembly SHA-256 등)이 바뀌었는지 먼저 확인합니다. 바뀌었으면 모드가 패치하는 함수들이 그대로인지 다시 봅니다.
